> 기획자는 **API 를 아예 안 쓰고 상세 페이지에 "유튜브 검색 링크" 한 줄**만 넣는다.
> 쿼터 문제·키 보관·오매칭 위험이 전부 사라진다. 사용자가 구현을 허락하면 **그 안을 쓴다.**
>
> 🆕 기획자가 찾은 제약 하나는 내 스케치에 없던 것이다 —
> **홈 카드는 `<a class="c">` 가 카드 전체를 감싸서 중첩 링크가 HTML 위반이다.**

>
> ⚠️ WO-4 는 **편의점 상품명 정규화(B-14)를 선행조건**으로 잡고 있다 —
> `CJ)얼큰우동221g(큰컵)` 으로 유튜브를 검색하면 결과가 안 나온다.

아래는 내 원래 스케치다. 기획자 안과 비교용으로 남긴다.

사용자가 예약한 다음 단계다. 아래는 **스케치**이고 착수 승인 전에는 코드를 쓰지 않는다.

**무엇을 만드나**
상품 상세(`/p/…`)에 "이 제품 영상으로 보기" 한 줄/한 칸. 홈 카드에는 **넣지 않는다**
(홈은 이미 300장 × 213KB 다. 영상 썸네일을 300개 얹으면 무너진다).

**이 사이트의 제약 — 여기서 설계가 거의 결정된다**

| 제약 | 결과 |
|---|---|
| 서버가 없다(GitHub Pages 정적) | 런타임 검색 불가. **빌드 타임에 찾아서 HTML 에 박는다** |
| 레포가 공개다 | API 키를 코드·HTML 에 넣을 수 없다. Actions Secret 으로 **빌드 때만** 사용 |
| YouTube Data API 일일 쿼터 10,000 | `search.list` 가 **1회 100 유닛** → 하루 약 100건이 상한 |
| 매일 06:00 전량 재빌드 | 전 상품(6,800건) 재검색은 쿼터의 68배. **캐시가 선택이 아니라 필수** |

**설계 스케치**

1. **캐시 우선.** `data/youtube.json` 에 `{상품키: {videoId, title, channel, publishedAt, checkedAt}}`.
   이미 있는 상품은 **검색하지 않는다.**
2. **신규분만 질의.** 하루 새로 등장하는 상품은 보통 수십 건이다(오늘 383건은 브랜드 합류분이라 예외).
   **1일 상한을 코드에 박고**(예: 80건) 넘치면 다음 날로 미룬다. 넘긴 건을 로그에 남긴다.
3. **"모르면 None".** 검색 결과를 그냥 쓰면 **엉뚱한 영상이 붙는다** — 이게 이 기능의 유일한 실패 모드다.
   통과 조건을 좁게 건다:
   - 영상 제목에 **브랜드명과 상품명 핵심 토큰이 모두** 들어갈 것
   - `publishedAt` 이 상품 날짜 ±N일 안일 것(날짜 없는 상품은 이 조건을 못 쓴다 → **B-13 과 연결된다**)
   - 하나도 통과 못 하면 **링크를 안 건다.** 억지로 붙이느니 없는 게 낫다
     (`Item.is_new` 의 삼상 계약과 같은 정신이다)
4. **표시.** 공식 iframe 임베드(YouTube API 서비스 약관이 요구하는 방식).
   썸네일만 긁어다 쓰지 않는다. 지연 로드로 상세 페이지 무게를 지킨다.
5. **되돌릴 수 있게.** 캐시 파일 하나만 지우면 원상복구. `collectors/` 계약은 건드리지 않는다
   — `Item` 에 필드를 늘리면 어댑터 46개가 전부 영향권이다.
   **별도 파일 + 빌드 타임 조인**이 맞다.

**먼저 답해야 할 것 (착수 전)**
- API 키를 누가 발급하고 어디에 둘 것인가 — **사용자 결정 필요**
- 날짜 없는 상품 260/300 에 대해 ③의 날짜 조건을 포기할 것인가, **B-13 을 먼저 할 것인가**
- 영상이 없는 상품이 대다수일 텐데(편의점 POS 상품은 거의 없을 것) 그 빈칸을 어떻게 보일 것인가
- 광고·협찬 영상이 붙는 것을 허용할 것인가

**난이도** 높음 / **선행조건** B-01 · (권장) B-13 · B-14
