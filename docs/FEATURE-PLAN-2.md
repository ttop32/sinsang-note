## 1. 라이브 재검수 (2026-10-01)

검수 중에 사이트가 **한 번 재배포됐다**. `00:34 빌드(227장)` 로 시작해 `10:59 빌드(300장)` 로 끝났다.
아래 수치는 전부 **10:59 빌드** 기준이고, 00:34 빌드에서만 본 것은 따로 표시했다.

### 1-1. 고쳐져 있는 것 (확인함)

| 항목 | 상태 |
|---|---|
| 홈 `<head>` (S12) | ✅ canonical · og:* · icon · apple-touch-icon · manifest · feed alternate 전부 있음 |
| 카드 이미지 정사각 (S11) | ✅ 375px 에서 164×164. 카드 368px |
| 탭 숫자 = 카드 수 (S5) | ✅ 편의점 121 + 카페 80 + 외식 99 = 300. `data-p` 실측과 일치 |
| 1단 4탭 폭 (§5-2) | ✅ 375px 에서 **339px** — 들어감 |
| 필터·검색·정렬 동작 (§6-1) | ✅ 카페 클릭 → 80장, `라떼` 검색 → 28장, 정렬 토글 동작 |
| NEW 뱃지 중복 (S3) | ✅ `DUP_LABELS` 로 제거됨 |

### 1-2. 아직 틀린 것 — 전부 이번 빌드에서 직접 봤다

**① 푸터·리드가 483건이라는데 화면엔 300장뿐이다 (38%가 숫자에만 있다)**

푸터: `마지막 갱신 2026-10-01 10:59 · 최근 60일 신제품 483건`
화면: `.c` 카드 **300장**, 전체 칩 **300**.

`collect.py:SHOW = 300` 이 자르는데 푸터·리드는 `len(rows)`(=483)를 쓴다.
PRODUCT-PLAN S5 에서 지적한 "숫자와 내용이 다르다"가 **같은 자리에 다시 생겼다.**
그때는 2장 차이였고 지금은 **183장 차이**다.

**② 잘린 183건과 함께 카테고리 3개가 통째로 사라졌다**

`docs/c/` 에는 디렉터리가 15개 있는데(`과자 도시락 디저트 라면 베이커리 분식 샌드위치 샐러드
일식 치킨 카페 편의점 피자 한식 햄버거`), 홈 2단 칩에는 **10개만** 있다.

| | 2단 칩 | `/c/` 페이지 | 사이트맵 |
|---|---|---|---|
| 한식 (8건) | ✗ | ✓ | ✓ |
| 도시락 (11건) | ✗ | ✓ | ✓ |
| 과자 (2건) | ✗ | ✓ | ✓ |

`/c/` 페이지는 `fresh`(483)로 만들고 2단 칩은 `shown`(300)으로 만들기 때문이다.
**검색엔진에는 있고 사용자에겐 없는 페이지**가 3종 생겼다.

**③ 2단 칩이 선언 순서대로다 — 큰 게 뒤에 숨는다**

실측 순서: `라면41 · 햄버거3 · 피자12 · 치킨4 · 베이커리26 · 디저트6 · 분식1 · 일식40 · 샌드위치4 · 샐러드3`

375px 에서 2단 줄은 `scrollWidth 735px / clientWidth 375px` 로 **절반이 화면 밖**이다.
그 밖에 있는 것 중에 **일식 40건**(두 번째로 큰 분류)이 있고, 화면 안에 있는 것은
**햄버거 3 · 치킨 4** 다. 작은 걸 보여주고 큰 걸 숨긴다.

**④ 가로로 밀린다는 표시가 없다**

`nav{overflow-x:auto;scrollbar-width:none}` + `nav::-webkit-scrollbar{display:none}`.
2단도 `.subnav` 가 같다. 375px 에서 10칩 중 4.5개만 보이는데 **잘린 칩의 절반이 보이는 것**이
유일한 단서다. 스크롤바도 그라데이션도 없다.

**⑤ 카페·편의점을 누르면 2단 줄이 통째로 사라진다**

`syncSub()` 가 `subnav.hidden = !any` 를 한다. 실측: 카페 클릭 → 보이는 2단 칩 **0개** → 줄이 사라지고
카드가 **59px 위로 점프**한다. 2단 분류(`brand_sub`)가 프랜차이즈에만 있어서 그렇다.

**⑥ og:image 가 파리바게뜨 CDN 이미지 한 장이다**

```
og:image = https://d2afncas1tel3t.cloudfront.net/wp-content/uploads/2026/09/크림치즈말랑.png
```

카톡·슬랙에 홈 링크를 던지면 **파리바게뜨 빵 사진 한 장**이 신상노트의 얼굴이 된다.
그 브랜드가 이미지를 내리면 공유 카드가 깨진다. 매일 바뀌므로 어제 공유한 링크와
오늘 공유한 링크가 다른 브랜드를 보여준다.

**⑦ 푸터가 두 줄뿐이다 — 게시중단 창구도, 범위 안내도 없다**

```
마지막 갱신 2026-10-01 10:59 · 최근 60일 신제품 483건
상품 정보와 이미지의 저작권은 각 브랜드에 있습니다.
```

`docs/CRAWLING-POLICY.md §5.5` 는 "요청이 오면 즉시 내린다"고 써놨는데
**요청을 받을 창구가 사이트 어디에도 없다.** 그리고 굿즈 178건·주류 2건이
조용히 빠지거나 조용히 남는데 그 사실이 화면에 없다.

**⑧ 주류가 아직 피드에 있다**

현재 창(483건) 안의 주류 2건 — `롯데)옐로우테일오로라팩(까버)`(와인),
`롯데)클라우드468ml캔(6입)`(맥주). 전체 카탈로그에는 **150건 안팎**이 있다(§3 F6 실측표).

**⑨ 카드 300장 중 243장(81%)이 외부로 나간다**

내부(`/p/...`) 57장 / 외부 243장. `card()` 가 "상품 URL 이 없거나 브랜드 대표 URL 과 같으면
내부로" 떨어뜨리는데, 그 조건에 걸리는 게 483건 중 **94건**(스시로 40 · 스타벅스 32 · 빽다방 11 ·
메가 6 · 프랭크버거 3 · 파파존스 1 · 할리스 1)뿐이다.
→ **이건 지금 돌고 있는 "카드 URL 백필" 작업의 영역이라 여기서 다시 기획하지 않는다.**
   다만 §3 F1(유튜브)이 이 판단 규칙에 얹히므로 §3 F1-3 에 동작 규칙만 적었다.

**⑩ 편의점 상품명이 아직 POS 코드다 (483건 중 92건)**

`CJ)얼티브프로틴초코250ml` · `널담)카스테라40g(초코)` · `오뚜기)뿌셔뿌셔불고기맛90g` ·
`[파란라벨]통곡물 호밀 깜빠뉴`. PRODUCT-PLAN P0-3 미적용 상태.
**이것이 §3 F1(유튜브)의 선행 조건이다** — 검색어로 쓸 수 없는 이름이다.

## 2. 경쟁 서비스 실측

열어본 것만 적는다. 열지 못한 것은 아래 "미확인"에 따로 모았다.

### 2-1. もぐナビ(mognavi.jp) `/newitem` — 일본 식품 신제품 DB

이 장르에서 가장 오래 돌아가는 서비스다. 열어서 본 것:

| 본 것 | 수치·형태 |
|---|---|
| **발매일 달력** | 월 단위 그리드. 날짜 칸마다 건수가 찍혀 있다 — `9/29 263` · `9/30 35` · `10/1 101` · `10/6 117` |
| **일자별 URL** | `/newitem/20261001` 형태. 미래 날짜(`/newitem/20261110`)도 링크돼 있다 |
| **전일 / 翌日 이동** | 목록 상단에 `前日 · 10月1日(木) · 翌日` |
| **브랜드로 묶어 출력** | `セブン-イレブン` 11건 → `第一パン` 7건 … 브랜드 소제목 아래 상품이 붙는다 |
| **메타** | 발매일 · 가격 · 칼로리 · **판매지역** · 원재료 설명 |
| **태그 축** | `#おつまみ` `#野菜` `#コンビニスイーツ` — 카테고리 탭과 별개의 가로축 |
| **회원 기능** | `食べたい N`(먹고싶다 카운터) · 클치코미(리뷰). **회원 등록·로그인이 전제다** |

**가져올 것 — 날짜가 1급 객체다.** 우리 서비스의 정의가 "그날 나온 것"인데
**지금 '그날'을 가리킬 URL 이 없다.** 홈은 매일 덮어써지고, 어제 본 걸 다시 찾을 방법이 없고,
카톡방에 "10월 1일 신상" 을 던질 단위가 없다. → §3 F9.

**가져올 것 — 날짜 칸의 건수.** 달력에 숫자가 있으니 "어느 날이 풍년인지"가 한눈에 보인다.
우리는 날짜 분포가 고르지 않다(실측: 60일 창 안 40개 날짜, 하루 1~25건).

**버릴 것 — 먹고싶다·리뷰.** 로그인이 전제다. 서버가 없다.
`localStorage` 로 흉내 내면 숫자가 항상 0 이나 1 이라 **빈 상호작용 UI** 가 된다
(PRODUCT-PLAN §4 가 이미 금지한 것).

**보류 — 태그 축.** 좋은 구조지만 우리 상품명이 아직 POS 코드라(§1-2 ⑩)
태그를 뽑을 수 없다. PRODUCT-PLAN §5-7 의 "정규화 전에는 장르 분류 금지"와 같은 판정이다.

### 2-2. YouTube 검색 결과 — 유튜브 기능의 근거

§3 F1 이 이 측정 위에 서 있다. 실제 상품 3건으로 검색해봤다.

| 검색어 | 상품의 날짜 | 1페이지 상위 결과 |
|---|---|---|
| `파리바게트 크림치즈말랑` | **2026-10-01 (당일)** | 🔴 **관련 영상 0건.** `프랑스 사람들을 혼란에 빠뜨린 바게트`, `정승제 치즈롤 리뷰`, `크림치즈 1kg를 산 나`, `뚜레쥬르와 파리바게트 비교`. 유튜브가 상품명을 버리고 `파리바게트` 로만 매칭했다 |
| `버거킹 몬스터 맥시멈` | 약 1개월 전 | 🟢 **상위 6건 전부 정타.** `단품 19600원, 버거킹 몬스터 맥시멈3 비교 리뷰`(5.8만) · `버거킹 몬스터 맥시멈 버거 리뷰`(4.9만) · `버거킹 몬스터맥시멈3… 크기도 칼로리도`(2.5만) |
| `메가커피 신메뉴` | (브랜드 단위) | 🟠 **섞인다.** 상위에 신메뉴 리뷰도 있지만 `[자막뉴스] "은퇴자금까지 부었는데" 날벼락...잘 나가던 메가커피의 민낯 / YTN`(165만회), `프렌차이즈 "로열티로 바꾸면 본사는 땡큐"` 가 같이 뜬다 |

읽어야 할 것이 셋이다.

1. **당일 신상에는 영상이 없다.** 당연하다 — 오늘 나온 걸 오늘 리뷰할 수 없다.
   그런데 우리 서비스의 1면은 **전부 당일~며칠 전 상품**이다(실측: 오늘 25건).
   "유튜브 보기"를 전건에 달면 **가장 눈에 띄는 카드일수록 엉뚱한 영상이 뜬다.**
2. **상품명이 길고 또렷하면 정확하다.** `몬스터 맥시멈` 은 완벽했다.
   차이는 **시간**(1개월)과 **화제성**(조회수 2.5~5.8만)이다.
3. **`신메뉴`·`신상` 을 검색어에 붙이면 안 된다.** 브랜드 평판 뉴스가 딸려온다.
   메가커피 사례가 그 증거다. 우리가 브랜드에 트래픽을 돌려주겠다고 해놓고
   그 브랜드의 가맹점 피해 뉴스로 보내는 건 최악이다.

### 2-3. Product Hunt — "오늘 나온 것" 피드의 원형

`Top Products Launching Today` + 순위 + 일자별 리더보드 아카이브.
**순위가 핵심인데 그건 투표(서버)다.** 우리에게 가져올 것은 **일자별 아카이브 URL** 하나뿐이고,
그건 §2-1 에서 이미 얻었다. 더 볼 게 없다.

| 배달의민족 · 쿠팡이츠 "신메뉴" 섹션 | 앱 전용. 웹에 같은 화면이 없다 |

## 3. 기능

우선순위는 PRODUCT-PLAN 과 같은 뜻으로 쓴다.
**P0 = 지금 신뢰가 깨지고 있다 / P1 = 재방문·유입을 만든다 / P2 = 그 다음 / P3 = 나중**

---

### F1. 제품별 유튜브 리뷰 — **검색 링크로 시작한다. API 는 조건부다.** `P0`

운영자가 "다음 기획"으로 지목한 항목이다. 결론부터 적는다.

> **상세 페이지(`/p/...`)에 "유튜브에서 리뷰 찾기" 링크 한 줄을 넣는다.
> 홈 카드에는 넣지 않는다. YouTube Data API 는 지금 쓰지 않는다. 임베드는 안 한다.**

#### F1-1. 왜 검색 링크인가 — 세 방식을 수치로 비교

| | ① 빌드 때 API 로 영상 ID 를 박는다 | ② 클릭 시 유튜브 검색 URL | ③ 임베드 |
|---|---|---|---|
| **외부 할당량** | 🔴 **하루 `search.list` 100콜** (아래) | 🟢 0 | ②·① 에 종속 |
| **비밀값 관리** | API 키를 GitHub Secrets 에 | 없음 | — |
| **빌드 시간** | +100콜 ≈ 수십 초 ~ 수 분 | 0 | 0 |
| **페이지 무게** | 0 (ID 문자열) | 0 | 🔴 iframe 1개 수백 KB |
| **오매칭 시 사용자가 보는 것** | 🔴 **엉뚱한 영상이 우리 페이지 안에 붙어 있다** | 🟠 유튜브 검색 결과가 비어 보인다 | 🔴 엉뚱한 영상이 재생된다 |
| **오매칭 책임** | 우리 | 유튜브 | 우리 |

**할당량 — 추정이 아니라 공식 문서 문장이다.**
[YouTube Data API · Quota Costs](https://developers.google.com/youtube/v3/determine_quota_cost) 에
그대로 쓰여 있다 — *"Projects that enable the YouTube Data API have a default quota allocation of
100 `search.list` calls, 100 `videos.insert` calls, and 10,000 units per day combined for all other
endpoints."* 즉 **검색은 하루 100번이 상한**이고, 상한을 넘기면 `403 quotaExceeded` 가 떨어진다.

우리 수치에 대보면:

| | 건수 | 하루 100콜로 |
|---|---:|---|
| 현재 창(60일) 신제품 | **483** | 백필에 **5일** |

| 과거 피크 (PRODUCT-PLAN §2 S9, 09-30 빌드) | **107** | 🔴 **그날 분을 다 못 채운다** |

하루 신규가 100건을 넘는 날이 실제로 있었다. 그날은 조용히 일부가 누락되거나
빌드가 `403` 으로 깨진다. **"GitHub Actions 일 1회"라는 전제 위에서 할당량이 빠듯하다.**

**오매칭 — §2-2 측정이 전부다.** 당일 신상에는 영상이 없고, 그런데도 `search.list` 는
**빈 결과가 아니라 '브랜드만 맞는 아무 영상'을 1위로 돌려준다**(파리바게뜨 사례).
API 를 쓰면 그 영상이 **우리 페이지 안에** 붙는다. 검색 링크는 같은 결과를
**유튜브 안에서** 보여준다. 똑같이 나쁜 결과인데 **누구의 화면에서 벌어지느냐**가 다르다.

PRODUCT-PLAN §7-11 의 원칙이 그대로 적용된다 — **오탐이 미탐보다 훨씬 나쁘다.**
링크가 없는 건 사용자가 모르고 지나간다. 틀린 영상이 붙어 있는 건 사용자가 본다.

#### F1-2. 구체적 동작

**어디에** `/p/<brand>-<name>/` 상세 페이지. `dl.f` 표(브랜드·유형·카테고리·등록일) 바로 아래.

**무엇을 보고 무엇을 누르나**

> 🔎 **유튜브에서 「버거킹 몬스터 맥시멈」 리뷰 찾기 →**

누르면 새 탭으로 `https://www.youtube.com/results?search_query=버거킹+몬스터+맥시멈`.
`rel="noopener nofollow"`, `target="_blank"` — 카드 외부 링크와 같은 규칙.

#### F1-3. 카드 URL 백필과의 관계 (중복 기획 아님 — 경계만)

지금 돌고 있는 "카드 URL 백필" 작업과 F1 은 **같은 판단을 공유한다**:
`url` 이 비었거나 브랜드 대표 URL 과 같으면 "이 제품의 페이지가 없다"는 뜻이다(현재 94건).

F1 쪽에서 지키는 규칙만 적는다.

- **유튜브 링크는 상품 URL 유무와 무관하게 단다.** 둘은 다른 질문이다
  (하나는 "브랜드 공식 정보", 하나는 "남의 후기").
- **상세 페이지에서 두 링크의 순서는 브랜드 먼저, 유튜브 나중.**
  이 서비스는 트래픽을 브랜드로 돌려주는 게 원칙이다(PRODUCT-PLAN §1).
- **홈 카드의 CTA 문구는 건드리지 않는다.** 그건 백필 작업자 영역이다.

**🟢 2026-10-01 백필 작업자 실측 — 94건 중 62건은 영구히 내부 링크다.**
백필 작업자가 12개 브랜드를 브라우저로 실측한 결과,
상품별 주소가 **브랜드 서버에 존재하지 않는** 곳이 대부분이었다.
스시로 40(카드가 `div[role=button]`, 모달 1개 재사용, 식별자 없음) · 빽다방 11 · 메가 6 ·
프랭크버거 3 · 할리스 1(`menuShare.do` 가 `idx` 를 무시하고 항상 카테고리 첫 상품) ·
파파존스 1. 스타벅스 32건은 어댑터가 이미 `product_cd` URL 을 만들고 있어 다음 수집에 자동 해소된다.
→ **`url` 이 없는 것은 수집 실패가 아니라 브랜드의 사실이다.** 더 파지 마라.

**🟢 결정 — 상세 페이지의 "브랜드로 나가는 링크"는 메뉴판이어도 된다. 단 문구를 바꾼다.**

PRODUCT-PLAN S2 가 금지한 것은 **홈 카드**가 메뉴판으로 보내는 것이다.
그때의 피해는 "사용자의 유일한 클릭이 맥락 없는 메뉴판에 떨어진다"였다.
상세 페이지는 다르다 — 사용자가 **이미 사진·설명·날짜를 보고 난 뒤** 스스로 더 보러 나가는 것이다.

| 상세 페이지의 외부 링크 | 문구 |
|---|---|
| 상품별 URL 이 있다 | `브랜드에서 보기 →` |
| 브랜드 대표 URL 뿐이다 (62건) | **`브랜드 메뉴판에서 보기 →`** |

**없는 걸 있는 척하지 않는 게 이 프로젝트의 계약이다**(ROADMAP §3-6 "모르면 None").
문구를 갈라두면 사용자가 무엇이 열릴지 알고 누른다.

**🟢 결정 — 라이트박스 딥링크(`#lg=…&slide=N`)는 규칙 1(외부)로 본다.**

김밥천국 `https://kimbab1009.com/31#lg=…&slide=6` 같은 형태.
문서는 목록 페이지지만 **열면 그 상품의 라이트박스가 열린 채로 뜬다**(작업자가 3건 스크린샷 확인).
즉 S2 의 피해("그 제품을 다시 찾아야 한다")가 없다. 사이트가 공유용으로 제공하는 주소이지
우리가 지어낸 주소도 아니다.

🟠 **단 `slide` 가 위치값이라는 한계를 기록해 둔다.** 브랜드가 갤러리 순서를 바꾸면
같은 브랜드의 **다른 상품**이 열린다. 수집이 매일 당일 HTML 에서 다시 뽑으므로
어긋나는 창은 길어야 하루다. 피해 상한이 "같은 브랜드의 다른 신메뉴가 열린다" 라서 받아들인다.
**다만 다른 브랜드에 같은 패턴을 복사하기 전에는 그 사이트도 같은 조건인지 확인해라** —
할리스 `menuShare.do?idx=` 는 겉모습이 비슷한데 **idx 를 아예 무시한다**(작업자 실측).

#### F1-4. 왜 홈 카드에 안 넣는가 — 기술 제약 + 측정값

**① 중첩 링크가 안 된다.** `collect.card()` 가 카드 **전체**를 `<a class="c">` 로 감싼다.

```html
<a class="c" href="https://www.paris.co.kr/..."> … <span class="go">브랜드에서 보기 →</span></a>
```

`<a>` 안에 `<a>` 를 넣는 건 HTML 위반이고 브라우저가 파싱 중에 바깥 `<a>` 를 닫아버린다.
유튜브 버튼을 카드에 넣으려면 **카드 구조를 통째로 바꿔야 한다**(`<a>` → `<article>` + 안쪽에
링크 2개). 그건 CSS·JS·필터·정렬이 전부 `.c` 를 전제로 돌고 있어서 **이 프로젝트에서 두 번
사이트를 죽인 종류의 변경**이다(PRODUCT-PLAN 서두 — CSS 로 한 번, JS 로 한 번).

**② 카드가 높아진다.** 375px 실측 카드 높이 **368px**, 첫 카드 top **355px**,
전체 문서 **43,761px (53.9 화면)**. 줄 하나(약 24px)를 300장에 더하면 **+7,200px**.
PRODUCT-PLAN P1-3 이 586 → 371px 로 줄여놓은 걸 되돌리는 방향이다.

**③ 홈의 용건이 아니다.** 홈은 "오늘 뭐 나왔나"를 5초에 훑는 곳이다.
"이거 어떤 맛이지"는 그 다음 단계이고, 그게 상세 페이지의 용건이다.
**그리고 상세 페이지는 지금 홈에서 링크가 57장뿐이라 들어갈 이유가 부족하다
— F1 은 상세 페이지에 들어갈 이유를 하나 만들어 준다.**

#### F1-5. API 로 승격하는 조건 (지금은 하지 않는다)

나중에 ①로 갈 수 있다. 그때 반드시 함께 들어가야 하는 것:

1. **캐시 파일** `data/youtube.json` — `{상품 key: {videoId | null, checked_at}}`.
   한 번 찾은 건 다시 안 찾는다. `null` 도 저장하고 **30일 뒤에만 재시도**.
   이게 없으면 483건이 매일 100콜 상한에 부딪힌다.
2. **하루 콜 상한을 코드에 박는다** (예: 80). 남으면 오래된 `null` 부터 재시도.
   상한을 넘으면 **조용히 멈추고 빌드는 성공시킨다.** 유튜브 때문에 수집이 깨지면 안 된다.
3. **결과를 그대로 믿지 않는다 — 가드 2개.**
   - **제목 포함 검사**: 영상 제목에 정규화된 상품명이 통째로 들어 있지 않으면 버린다.
     §2-2 의 `프랑스 사람들을 혼란에 빠뜨린 바게트` 는 이 검사 하나로 걸러진다.
   - **게시일 검사**: 영상 게시일이 상품 날짜보다 **이전이면 버린다.** 옛 영상이다.
   - 둘 중 하나라도 실패하면 `videoId` 를 비우고 **②(검색 링크)로 떨어진다.**
4. **매칭률이 낮게 나오는 게 정상이다.** 가드를 넣으면 많이 버려진다. 그게 설계 의도다.
5. **🟠 미확인 — YouTube API 서비스 약관.** API 로 가져온 데이터를 쓸 때
   재생 요구사항·브랜딩 요구사항이 걸릴 수 있다. **승격 전에 약관을 직접 읽고
   `docs/CRAWLING-POLICY.md` 에 한 절을 추가해야 한다.** 이 문서는 그걸 확인하지 않았다.
   (②번 검색 링크는 그냥 링크라 이 문제가 없다 — 이것도 ②를 먼저 하는 이유다.)

**임베드(③)는 ① 다음이다.** videoId 가 있어야 하고, 넣더라도 **상세 페이지에서만, lite 방식**
(`https://i.ytimg.com/vi/<id>/hqdefault.jpg` 썸네일 ~20-40KB → 클릭하면 그때 iframe 교체).
홈에는 어떤 형태로도 넣지 않는다.

**우선순위** **P0** — 운영자 지목 1순위. 단 **들어가는 것은 ②(검색 링크)뿐**이고
그건 파일 2개·함수 1개다. ①은 조건이 갖춰지면 **P2** 로 다시 올린다.

**정적 사이트에서 되는가 — 되지만 생성기를 그대로 못 쓴다**

여기가 중요하다. `collect.main()` 은 `pages.build(fresh, rows, docs)` 를 부르고,

```python
if r.get("nonfood"):

```

이다. 즉 **굿즈는 `fresh` 에 절대 안 들어간다.** `pages.build()` 는 `fresh` 만 돌므로

| 파일 | 무엇을 |
|---|---|
| `collect.py` `main()` | `fresh` 와 **별개로** `goods` 리스트를 만든다 (`nonfood=True` + 같은 날짜 판정 + `merge_variants`·`drop_sets`·`cap_per_brand` 동일 적용) |

**상세 페이지(`/p/...`)는 만들지 않는다.** 굿즈 65건의 상세를 만들면
`"할리스 더 가벼운 텀블러 — 신제품 | 신상노트"` 같은 비식품 페이지가 색인된다.

→ `goods_page` 의 카드는 `/p/` 가 아니라 **브랜드 상품 URL(외부)로 직접** 나가게 한다.

**비용/위험**

- 페이지 무게: 65장 × 약 570바이트 ≈ 40KB.
- 🟠 **할리스 13건이 텀블러 색상 변형일 가능성.** PRODUCT-PLAN §7-9 ② 가 지적한 건

  **생성 후 눈으로 한 번 훑는다**(13장이면 사람이 훑는 게 싸다).
- 🟠 **`is_nonfood()` 단어 목록 변경과 묶어서 하지 마라.** PRODUCT-PLAN §7-12 의
  `핸디` 삭제·`머그컵`→`머그`·`굿즈`/`가방`/`세제` 추가는 **이미 적용돼 있다**
  (`collectors/base.py:186-191` 실측 확인). 다시 건드릴 일이 없다.

**우선순위** **P1.** 비용이 거의 0 이고 PRODUCT-PLAN §8-2 의 2'' 로 이미 예약돼 있다.

### F4. 2단 칩 — 건수 내림차순 + 가로 스크롤 힌트 `P1`

**왜** §1-2 ③④. 지금 **일식 40건**(2위)이 8번째라 375px 화면 밖에 있고,
화면 안에는 **햄버거 3 · 치킨 4** 가 있다. 그리고 옆으로 밀린다는 표시가 없다.

**구체적 동작**

**① 정렬 — 건수 내림차순.** `collect.py:render()` 의

```python
for k in SUBS if scount.get(k)
```

를 `scount` 건수 내림차순(동률이면 `SUBS` 선언 순)으로 바꾼다.
적용하면: `라면41 · 일식40 · 베이커리26 · 피자12 · 디저트6 · 치킨4 · 샌드위치4 · 햄버거3 · 샐러드3 · 분식1`
→ 375px 첫 화면에 **라면·일식·베이커리**(107건, 전체 2단의 65%)가 들어온다.

**② 가로 스크롤 힌트 — 오른쪽 끝 12px 그라데이션.**

🔴 **구현 함정이 있다.** `.subnav` 자체가 `overflow-x:auto` 라서 거기에 `::after` 를 붙이면
**그라데이션이 칩과 같이 스크롤돼 오른쪽 끝으로 사라진다.** 래퍼를 하나 더 두고
(`position:relative`) 그 위에 `::after{position:absolute;right:0;pointer-events:none}` 를 얹어야 한다.
또는 스크롤 컨테이너에 `mask-image:linear-gradient(to right,#000 calc(100% - 16px),transparent)` 를 건다
(🟠 미확인 — 사파리 구버전 접두 필요 여부를 확인하지 않았다. `::after` 쪽이 안전하다).
1단 `nav` 도 같은 처리를 한다(현재 339/375 라 안 밀리지만, 칩이 하나라도 늘면 밀린다).

**③ "2단 배치"에 대한 판정 — 칩을 두 줄로 깔지 마라.**

운영자 숙제의 "2단 배치"를 **칩을 두 줄 wrap** 으로 읽을 수도 있어서 재봤다.

| 안 | 375px 결과 | 판정 |
|---|---|---|
| 현재 — 1줄 가로스크롤 | `scrollWidth 735 / clientWidth 375` · 4.5칩 보임 · 첫 카드 top **355px** | |
| 두 줄 wrap (10칩) | 줄당 약 368px · 전부 보임 · 첫 카드 top 약 **400px** | 🟠 |
| 두 줄 wrap (13칩, `SUBS` 전부 살아날 때) | **3줄**이 된다 · 첫 카드 top 약 445px | 🔴 |

**권고: wrap 하지 마라.** 이유 둘.
(a) 지금 375px 에서 첫 카드가 355px 아래에 있고 **첫 화면에 카드 1.3장**뿐이다.
    여기서 45px 를 더 쓰는 건 PRODUCT-PLAN P1-3(모바일 카드 높이 절반)과 반대 방향이다.
(b) 칩 개수가 데이터에 따라 변한다. 오늘은 10개지만 `SUBS` 는 13개고 `/c/` 는 15개다.
    **줄 수가 날마다 바뀌면 레이아웃이 매일 움직인다.**
→ 가로 스크롤을 유지하고 **①(중요한 걸 앞에) + ②(밀린다는 표시)** 로 푼다. 그게 "2단 배치"의 용건이다.

**④ 🟠 같이 보고만 한다 — 2단 줄이 사라지는 점프.** §1-2 ⑤.
카페·편의점에는 `brand_sub` 가 없어 2단이 통째로 숨고 카드가 59px 점프한다.
**이번 작업에서 고치지 마라.** PRODUCT-PLAN §6-2 가 "카페 2단에 `음료`·`디저트` 를 넣는다"로
이미 예약해 둔 자리다. 콘텐츠가 먼저다.

**정적 사이트에서 되는가** 전부 `collect.py` 안 (`CSS_EXTRA` 문자열 + `render()` 의 `subs` 생성부).

**비용/위험** 0. 🔴 **`CSS_EXTRA` 는 여러 줄 CSS 블록이다. 부분 치환 금지 — `nav{...}` 와
`.subnav{...}` 규칙을 통째로 다시 써라.** 이 프로젝트가 같은 실수로 두 번 죽었다.

**우선순위** **P1.**

### F5. og:image — **콜라주가 아니라 자체 생성 커버** `P1`

**왜** §1-2 ⑥. 지금 홈의 og:image 가 파리바게뜨 CDN 이미지 한 장이다.

**🔴 PRODUCT-PLAN §6-8 ② 의 "콜라주" 를 조건부로 반려한다.**

콜라주를 만들려면 브랜드 이미지 4~9장을 **다운로드해서 합성한 PNG 를 우리 도메인에 올려야**
한다. 지금은 `<img src="브랜드CDN">` 핫링크라 **브랜드 서버가 서빙**하고, 푸터의
"저작권은 각 브랜드에 있습니다"가 성립한다. 콜라주는 **우리가 사본을 만들어 재배포**하는 것이고,
이건 PRODUCT-PLAN §4 가 명시적으로 금지한 **"브랜드 이미지 자체 호스팅"** 그 자체다.
`CRAWLING-POLICY §3`(저작권 리스크)과도 충돌한다. 기능 하나 때문에 정책을 뒤집을 일이 아니다.

**대안 — 코드로 그린 커버.** `web/assets.py` 가 이미 **아이콘을 코드로 그리고
`zlib`+`struct` 로 PNG 를 직접 인코딩한다**(Pillow 없이). 같은 방식으로 1200×630 커버를 만든다.

```
┌────────────────────────────────┐
│  (브랜드 색 배경 + 아이콘 마크)      │
│  신상노트                         │
│  오늘 25건 · 최근 60일 300건        │
│  2026-10-01                     │
└────────────────────────────────┘
```

- 사진이 없는 게 약점이다. 대신 **매일 숫자가 바뀌어서 공유 카드가 신선해 보인다**
  (PRODUCT-PLAN P1-2 가 og:image 를 매일 바꾸려 한 이유가 이거다).
- 저작권·핫링크·깨짐 문제가 **전부 사라진다.** 브랜드가 이미지를 내려도 우리 커버는 그대로다.
- 한글 글자를 PNG 로 찍는 게 쉽지 않다. 🟠 **구현 난이도가 여기 있다.**
  `.venv` 에 폰트 래스터라이저가 없다. 방법 둘:
  (a) 숫자·로마자만 쓰는 디자인(`SINSANG 25 / 2026-10-01` + 마크) — 한글 없이.
  (b) 글자 몇 개를 `assets.py` 가 아이콘을 그리듯 **좌표로 직접 그린다**(획이 적은 글자만).
  → **(a)를 권한다.** 공유 카드의 제목·설명은 `og:title`·`og:description` 이 글자로 말해준다.
  이미지는 **브랜드 식별**만 하면 된다.

**🟠 미확인 — SVG 를 og:image 로 쓰는 것.** 카카오톡·슬랙 스크래퍼가 SVG 를 렌더하는지
직접 확인하지 않았다. `icon.svg` 가 이미 있으니 되면 공짜인데, **확인 전에는 PNG 로 간다.**

**정적 사이트에서 되는가** `web/assets.py` 에 `cover(stats)` 추가 → `docs/og.png` 출력.
`collect.py:render()` 의 `theme.head(..., image=...)` 인자를
`top["image"]` → `ROOT_PATH + "og.png"` 로 바꾼다 (1줄).
`/p/`·`/b/`·`/c/` 는 **지금처럼 그 페이지의 상품 이미지를 쓴다** — 그건 그 페이지의 내용이고,
핫링크라 자체 호스팅이 아니다. **홈만 바꾼다.**

**비용/위험** 빌드 +1초 미만, 파일 1개(수십 KB). 외부 요청 0.
🔴 `assets.py` 의 PNG 인코더를 건드리게 되니 **아이콘 4종이 그대로 나오는지 같이 확인해야 한다.**

**우선순위** **P1.** 공유 유입이 이 서비스의 주된 확산 경로인데 지금 남의 얼굴이 나간다.

### F7. Atom 피드 `<updated>` — **진단을 정정한다** `P1`

**왜 — PRODUCT-PLAN §3 P1-6 의 진단이 틀렸다.**

그 문서는 "`<updated>` 에 빌드 날짜가 들어간다 → 매일 50건 중복 알림"이라고 썼다.
코드를 읽고 실물을 보니 **그게 아니다.**

```python
# web/seo.py:145
when = _rfc3339(collect._when(r))        # 상품 날짜다. 빌드일이 아니다.
```

실물 `docs/feed.xml` 은 `<updated>` 51개가 전부 `2026-09-30T00:00:00Z` 인 게 맞다. 원인은 둘.

1. **`_when()` 이 날짜(일)만 준다.** 시·분·초가 전부 `00:00:00Z` 로 찍힌다.
2. **`FEED_MAX = 50` 인데 최신 하루에 50건 이상이 몰린다.** 그래서 상위 50이 전부 같은 날이 된다.

**중복 알림은 안 난다.** Atom 리더는 `<id>` 로 항목을 식별하고, `<id>` 는 상품 상세 URL 이라
이미 고유하다. 실물에서 확인했다.

**진짜 문제는 셋이다.**

| | 증상 |
|---|---|
| ① | 피드 자체 `<updated>` 도 상품 날짜(`2026-09-30`)다. 오늘 11시에 빌드했는데 피드는 "어제 자정에 갱신됨"이라고 말한다. 리더가 **폴링 주기를 늦출 수 있다** |
| ② | 50건이 전부 같은 타임스탬프라 **정렬이 리더 구현에 맡겨진다.** 최신순이 보장되지 않는다 |
| ③ | 하루 신규가 50건을 넘으면(실측: 09-30 빌드 **107건**) 그날 분이 **조용히 잘린다** |

**구체적 동작**

1. **피드 자체 `<updated>` 만 빌드 시각으로.** `_feed()` 의 `updated = _rfc3339(...)` → `_now()`.
   항목은 그대로 둔다.
2. **`<published>` 를 항목에 추가.** `<updated>` 와 같은 값. 리더가 "언제 나온 것"을 읽는 표준 자리다.
3. **`FEED_MAX` 50 → 100.** 실측 피크 107건을 담으려면 그래야 한다.
   피드 용량: 현재 57KB/50건 → 약 114KB. 허용 범위다.
4. **❌ 타임스탬프를 지어내지 마라.** "같은 날이면 i번째를 `00:00:{i}Z` 로" 같은 방식은
   없는 시각을 만드는 것이다. 이 프로젝트는 "모르면 None"을 계약으로 삼고 있다
   (ROADMAP §3-6). 정렬은 ①②로 충분히 좋아진다.
5. **푸터에 RSS 링크.** `<head>` 의 `rel=alternate` 는 이미 있다(실측 확인). 보이는 링크가 없을 뿐이다.
   **F3(푸터)와 같이 한다.** 단 1~3 이 끝난 뒤에 노출해라.

**정적 사이트에서 되는가** 전부 `web/seo.py`. 파일 하나다.

**비용/위험** 피드 용량 2배. 다른 영향 없음.

**우선순위** **P1.** 서버 없이 쓸 수 있는 유일한 진짜 구독 채널이다.

### F8. 숫자를 그리는 수와 맞춘다 (483 → 300) `P0`

**왜** §1-2 ①. 푸터·리드가 483이라 쓰고 화면엔 300장이다. **183장(38%)이 숫자에만 있다.**
PRODUCT-PLAN S5 에서 같은 종류의 문제를 2장 차이로 지적했고, 그때 "렌더된 카드에서 세도록"
고쳐서 **탭 숫자는 맞아졌는데 푸터·리드는 안 고쳐졌다.**

**구체적 동작** — `collect.py:render()` 안, 세 줄.

```python
shown = rows[:SHOW]
lead  = f"오늘 {len(new_today)}건" if new_today else f"최근 {WINDOW}일 신제품 {len(rows)}건"
footer … 최근 {WINDOW}일 신제품 {len(rows)}건
```

`len(rows)` → `len(shown)`. 그리고 **잘린 183건이 어디 있는지 한 줄로 말한다.**

> `최근 60일 신제품 483건 중 최신 300건 · 전체는 브랜드별 목록에서`

🔴 **`lead` 의 `오늘 N건` 은 `new_today` 를 쓰는데 `new_today` 는 `fresh`(483) 기준이다.**
`shown`(300)에 안 들어간 오늘자가 있으면 "오늘 25건"인데 화면엔 20장일 수 있다.
`new_today` 도 `shown` 기준으로 세라.

**같이 고칠 것 — 보이지 않는 `/c/` 페이지 3종.** §1-2 ②.
`한식`·`도시락`·`과자` 가 `/c/` 와 사이트맵에는 있고 홈 칩에는 없다. 둘 중 하나다.

- (a) 2단 칩을 `fresh`(483) 기준으로 센다 → 칩을 눌러도 카드가 안 나오는 분류가 생긴다. **안 된다.**
- (b) `/c/` 페이지도 `shown` 기준으로 만든다 → 색인 페이지가 줄어든다. SEO 손해.
- (c) **푸터에 "분류 전체 보기" 링크를 두고 `/c/` 15종을 거기서 연다.** ← **권고.**
  칩은 "지금 화면에서 거를 수 있는 것", `/c/` 는 "따로 한 장을 볼 수 있는 것" 으로 역할이 갈린다.
  PRODUCT-PLAN §8-3 B("홈에 브랜드 목록 링크")와 같은 자리에 들어간다.

**정적 사이트에서 되는가** 전부 `collect.py:render()` 안. F3·F4 와 **같은 파일**이다.

**비용/위험** 0.

**우선순위** **P0.** 화면에 쓴 숫자가 틀린 건 다른 어떤 기능보다 먼저다.

### F9. 일자별 아카이브 `/d/2026-10-01/` + 달력 `P2`

**왜** §2-1. mognavi 가 10년 넘게 그렇게 하고 있고, 우리에게 더 맞는 이유가 있다 —
**이 서비스의 정의가 "그날 나온 것"인데 '그날'을 가리킬 URL 이 없다.**
홈은 매일 덮어써진다. 어제 본 걸 다시 못 찾고, 카톡방에 "10/1 신상"을 던질 단위가 없고,
`10월 1일 편의점 신상` 같은 검색어가 닿을 페이지가 없다.

**구체적 동작**

- `/d/2026-10-01/` — 그날 날짜(`_when(r)`)인 신제품만. `_list_page()` 재사용.
- 페이지 상단에 `← 9월 30일 (18건) · 10월 1일 · 10월 2일 →` 전후 이동.
- 홈 푸터에 **최근 7일 링크** + `달력 보기`.
- `/d/` 인덱스에 **달력 그리드**(날짜 칸에 건수). mognavi 와 같은 형태.
  실측: 60일 창 안에 날짜가 **40개**, 하루 1~25건.
- 사이트맵에 추가. 피드에는 넣지 않는다.

**정적 사이트에서 되는가** 완전히 된다. `pages.build()` 가 이미 `by_brand`·`by_kind` 로
묶어 `_list_page()` 를 돌린다. `by_day` 를 하나 더 만들면 끝이다.
**달력은 HTML 테이블 + CSS 뿐이다**(JS 불필요).

**비용/위험** 페이지 최대 60장 추가(현재 `/p/` 502 + `/b/` + `/c/` 15). 빌드 +1~2초.
🟠 **하루 1건짜리 날짜 페이지가 생긴다.** "얇은 페이지"가 색인 품질을 깎을 수 있다.
→ **5건 미만인 날은 페이지를 만들지 않고 달력에서 숫자만 보여준다**(클릭 불가).
`pages.build()` 가 이미 "신제품이 없는 유형은 페이지를 만들지 않는다"를 하고 있으니 같은 패턴이다.

**PRODUCT-PLAN P2-1(주간 `/w/2026-W40/`)과 겹친다.** 둘 중 **일 단위를 권한다** —
수집이 일 1회이고 화면이 이미 "오늘 N건"으로 말하고 있다. 주 단위는 하루 건수가 모자랄 때의
보완인데 실측 하루 25건이면 한 장이 된다. **주간은 일간이 돌아간 뒤에 판단한다.**

**우선순위** **P2.** F1~F8 이 끝난 뒤.

### F10. 홈에 날짜 구분선 `P2`

**왜** 홈 300장이 날짜가 섞인 채 흐른다. §2-1 의 mognavi 는 날짜로 끊고 그 안에서 브랜드로 묶는다.
실측 날짜 분포: `10-01 25건 · 09-30 ? · 09-29 ? … 08-03 4건` — 60일에 40개 날짜.

**구체적 동작** 카드 사이에 `9월 30일 · 18건` 헤더. 필터·검색이 켜져 있을 때는 숨긴다
(`apply()` 가 카드만 `hidden` 토글하므로 **헤더가 혼자 남는 버그가 난다** — 이 처리가 필수다).

**정적 사이트에서 되는가** 된다. 다만 **`apply()` 를 건드려야 하고,
`sortBtn` 의 브랜드순 정렬이 `g.appendChild(c)` 로 DOM 순서를 바꾼다.**
날짜 헤더가 섞여 있으면 **브랜드순으로 바꿨을 때 헤더가 엉뚱한 데 남는다.**
→ 브랜드순일 때는 모든 헤더를 숨긴다. 🔴 **이게 "탭·검색이 통째로 죽은" 두 사고와 같은 자리다.**

**비용/위험** JS 변경. **F9 보다 위험하고 가치는 비슷하다.** F9 를 먼저 해라.

**우선순위** **P2.** F9 뒤.

## 4. 하지 말아야 할 것

**유튜브 영상을 홈 카드에 붙이기.** `card()` 가 카드 전체를 `<a>` 로 감싼다.
중첩 링크는 HTML 위반이라 카드 구조를 통째로 바꿔야 하고, 그건 `.c` 를 전제로 돌아가는
CSS·필터·검색·정렬을 전부 흔든다. **이 프로젝트에서 사이트를 두 번 죽인 그 자리다.**
게다가 줄 하나 × 300장 = 모바일 +7,200px.

**유튜브 검색어에 `신메뉴`·`신상` 붙이기.** 실측 — `메가커피 신메뉴` 상위에
`"은퇴자금까지 부었는데" 날벼락...잘 나가던 메가커피의 민낯 / YTN`(165만회)이 뜬다.
브랜드에 트래픽을 돌려주겠다면서 그 브랜드의 가맹점 피해 뉴스로 보낼 수는 없다.

**YouTube Data API 를 캐시·상한·가드 없이 붙이기.** 하루 `search.list` **100콜**이 상한이고,
우리 창에 483건이 있고, 하루 신규가 107건이던 날이 있었다. 캐시가 없으면 매일 상한에 부딪히고,
상한을 넘으면 `403` 으로 **수집 빌드 전체가 깨진다.**

**주류·비식품을 substring 단어 목록으로 거르기.** 전체 데이터에 대본 결과
`카스`→카스테라 54건, `막걸리`→막걸리향 콜드브루 2건(둘 다 식품), `청주`→청주식돼지김치짜글이.
**스타벅스 `핸디 젤리` 와 똑같은 사고를 내가 이 조사 중에 재현했다.**
새 단어는 **전체 6,835건에 대고 식품 오탐 0 을 세고 넣어라.**

**og:image 콜라주를 저작권 판단 없이 만들기.** 콜라주는 브랜드 이미지를 받아 합성해
**우리 도메인에서 재배포**하는 것이다. 지금의 핫링크와 법적 성격이 다르고,
PRODUCT-PLAN §4 와 `CRAWLING-POLICY §3` 이 금지한 것 그 자체다.

**찜·좋아요·먹고싶다 카운터.** mognavi 의 `食べたい N` 은 **회원 등록·로그인이 전제다**(실측).
우리가 `localStorage` 로 흉내 내면 숫자가 항상 0 이거나 1 이다.
**빈 상호작용 UI 는 서비스가 죽어 보이게 만든다**(PRODUCT-PLAN §4 가 이미 결론낸 것).

**`SHOW` 를 올려 483건 전부 그리기.** 현재 300장에 172KB · 모바일 **43,761px(53.9 화면)** 이다.
483장이면 약 270KB · 70,000px(86 화면)이 된다. 양이 문제인 걸 양을 늘려서 풀 수는 없다.
F8(숫자 정정) + `/c/`·`/b/`·`/d/` 로 내보내는 게 맞다.

**2단 칩을 두 줄로 wrap.** 375px 에서 첫 카드가 이미 355px 아래에 있다. 45px 를 더 쓰면
첫 화면에 카드가 1장이 된다. 게다가 칩 개수가 데이터에 따라 10~15개로 변해서
**줄 수가 매일 바뀐다.**

**날짜 헤더(F10)를 F9 보다 먼저.** `apply()`·`sortBtn` 을 둘 다 건드려야 하고,
그게 이 프로젝트에서 탭·검색이 죽은 자리다. 같은 가치를 위험 없이 주는 F9 를 먼저 해라.
