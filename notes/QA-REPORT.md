`collect.is_fresh()` 는 `is_new=True` + 날짜 없음이면 **무조건 True 를 돌려준다**(collect.py 의
"날짜가 없으면 배지를 그대로 믿는다" 분기). 그래서 날짜가 안 뽑힌 9건이 영구히 신제품 칸에 남는다.

가장 또렷한 증거는 같은 상품의 쌍이다:

- `디카페인오트밀라떼(H)` → 이미지명에 날짜가 있어 `uploaded_at=2025-09-19` → 1년 전이라 **걸러짐**
- `디카페인오트밀라떼(I)` → 이미지명에 날짜가 없음 → **신제품으로 노출**

같은 날 같은 분류에 올라온 한 상품인데 HOT 은 빠지고 ICE 는 신상으로 뜬다.
10월에 '엣날팥빙수'·'팥통통스무디'가 신제품으로 올라오는 것도 같은 경로다.

**고쳐야 할 것** — `bakery_breadnco.py:90` (`it.uploaded_at = _uploaded_at(src)`)
이미지 파일명에서 날짜를 못 뽑으면 `portfolio-sitemap.xml` 의 `lastmod` 로 채워라.
docstring(:20-22)이 이미 "portfolio-sitemap.xml 한 번으로 … lastmod 까지는 받을 수 있다"고
적어 놓고도 쓰지 않았다. 요청은 1회 늘고, 그 1회로 9건의 영구 오탐이 사라진다.

## 9. 카드 URL 백필 (`collectors/snack_kimbabcheonguk.py`) — **통과**

작성자 `a6239f22f847f3d7c`. 수정은 이 파일 1개뿐임을 `git diff` 로 확인했다

```

**핵심 가정(`data-no` = 라이트박스 순번)을 원본 HTML 로 직접 검증했다. 맞다.**

   slide=0  → 까르보나라   ✅
   slide=6  → 매운볶음우동 ✅
   slide=74 → 홍합탕       ✅
```
세 건 모두 작업자의 브라우저 확인 결과와 **일치한다**. 순번을 짐작하지 않고
`gallery_id` 나 `data-no` 가 없으면 빈 값으로 폴백하는 처리(`_url`)도 적절하다.

"0장 줄었다"는 자기 보고도 사실이다 — 62건 전부 `uploaded_at=2017-04-16` 이라
`collect.is_fresh()` 에서 걸러져 홈 300장에는 원래 한 장도 안 들어간다. 효과는
개별 상세 페이지(`web/pages.py`)의 브랜드 링크에만 난다. **과장 없이 적은 점이 좋다.**

남는 위험(결함 아님, docstring 에 이미 명시됨): `slide` 가 위치값이라 브랜드가 갤러리 순서를
바꾸면 어제 저장된 URL 이 다른 상품을 가리킨다. 매 수집마다 다시 뽑으므로 평상시엔 맞지만,

나머지 11개 브랜드는 코드를 건드리지 않았고(`git diff` 로 확인), "상품별 URL 없음" 근거는

### 12-3. H1 (결함) — 과반 실패 가드가 **캐시가 더운 날 과민하다**

`cafe_hollys.py` `_fill_is_new()` 끝의 `if tried and failed * 2 > tried:` 를 산술로 돌려봤다:

```
tried=  1 failed=  1 → 예외  ← ⚠️
tried=  2 failed=  2 → 예외  ← ⚠️
tried=  3 failed=  2 → 예외  ← ⚠️
tried=  2 failed=  1 → 통과
tried=238 failed=  1 → 통과
tried=238 failed=120 → 예외   ← 의도한 동작
```
첫 수집(238장)에서는 의도대로 동작한다. 문제는 **그 다음날부터**다.
작성자 설명대로 캐시가 더워지면 `tried` 는 그날 새로 생긴 상품 수(보통 1~3건)로 떨어진다.
그 상태에서 **이미지 한 장이 타임아웃 나면 `tried=1, failed=1` → `RuntimeError`** 가 나고,
`collect.py:144` 가 그걸 잡아 **할리스 238건이 통째로 실패 처리**된다(이전분 carry +
Actions 빨강). 신상 1건을 못 읽은 대가로 브랜드 전체가 그날 멈춘다.

이 어댑터가 막으려던 "조용한 전면 실패"와는 다른 방향의 사고다. 비율 가드에
**최소 표본 조건**을 붙여라. 예:
```python
if tried >= 5 and failed * 2 > tried:      # 또는  if failed == tried and tried >= 3
```
숫자는 운영자 판단이지만 `tried=1` 한 건으로 터지는 지금 상태는 고쳐야 한다.

### 15-1. TLS 중간인증서 보충 — **이 변경이 이번 검수에서 가장 위험할 수 있는 자리였다. 안전하다.**

레포에 CA 인증서를 커밋하는 변경이라 제일 먼저, 제일 세게 봤다.

**① 신뢰 범위가 넓어지지 않는다 (핵심).**
```
subject = CN=GlobalSign GCC R3 DV TLS CA 2020,  O=GlobalSign nv-sa,  C=BE
issuer  = CN=GlobalSign, OU=GlobalSign Root CA - R3        ← 공개 루트
openssl verify -CAfile $(certifi.where())  …pem   →  OK
```
상위 루트가 **이미 certifi 에 들어 있다.** 즉 이 파일은 새 신뢰 기점(root)이 아니라
**이미 신뢰하는 루트 밑의 중간 고리 한 칸**이다. 루트가 여전히 이 인증서를 검증해야 하므로
우리가 신뢰하는 범위는 한 치도 늘지 않는다. 루트 CA 를 번들에 끼워 넣는 것과는 질이 다르다.

**② 이 인증서로 또 다른 CA 를 만들 수 없다.**
```
X509v3 Basic Constraints: critical  CA:TRUE, pathlen:0
X509v3 Key Usage: critical  Digital Signature, Certificate Sign, CRL Sign
X509v3 Extended Key Usage:  TLS Web Server/Client Authentication
```
`pathlen:0` 이라 최종 엔티티 인증서만 발급할 수 있다. EKU 도 TLS 로 한정돼 있다.

**③ 검증을 끄지 않았다. 내가 직접 깨 봤다.**
```
ctx.check_hostname = True   ctx.verify_mode = 2 (CERT_REQUIRED)     ← 기본값 그대로

같은 컨텍스트로 실측:
  200   https://company.lottechilsung.co.kr/kor/product/newprdt/list.do
  FAIL  https://wrong.host.badssl.com/      CERTIFICATE_VERIFY_FAILED: Hostname mismatch
  FAIL  https://self-signed.badssl.com/     CERTIFICATE_VERIFY_FAILED: self-signed certificate
  FAIL  https://expired.badssl.com/         CERTIFICATE_VERIFY_FAILED: certificate has expired
  FAIL  https://untrusted-root.badssl.com/  CERTIFICATE_VERIFY_FAILED: self-signed … in chain
```
뒤의 둘(expired·untrusted-root)은 **작성자가 안 돌린 것을 내가 추가**했다. 전부 올바르게 막힌다.

**④ 오염 범위가 이 어댑터뿐이다.** `grep -rn "certs/|load_verify_locations|set_default_verify"
collectors/base.py collect.py` → **0건**. `ssl.create_default_context(cafile=certifi.where())`
위에 `load_verify_locations()` 로 **더하고**, 그 컨텍스트를 `base.client(verify=...)` 로만 넘긴다.
전역 기본 컨텍스트나 다른 어댑터에 영향이 없다.

**⑤ 출처 추적 가능.** pem 머리말에 AIA 주소·받은 날·SHA256 지문·`openssl verify` 확인법·
만료일(2029-03-18)·재발급 절차가 적혀 있고, 내가 잰 지문이 적힌 값과 일치한다
(`76:25:38:43:…:67:6E`). 리프 만료(2027-01-20) 시 **조용히 0건이 아니라 `ConnectError` 로
죽는다**는 점도 적혀 있다 — 이 레포 기준으로 올바른 실패 방향이다.

**판정: `verify=False` 를 쓰지 않고 중간인증서를 보충한 것은 옳은 해법이고, 구현도 안전하다.**
`CRAWLING-POLICY.md` §6-1 의 "중간인증서 보충은 다른 이야기다" 칸에 정확히 들어맞는다.
